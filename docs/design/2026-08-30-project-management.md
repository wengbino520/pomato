# 项目管理维度增强方案设计

> 创建时间：2026-08-30
> 状态：方案设计 / 待确认
> 对应路线图：Phase D · D1 项目管理维度
> 目标：为番茄记录、待办、日报与统计补齐“项目”这一稳定归属维度，替代当前仅靠扁平标签承载聚合语义的不足

---

## 0. 前置判断与假设

### 0.1 当前判断

基于 `docs/evolution-roadmap.md`、`README.md` 和当前源码，POMATO 已具备以下基础：

- 番茄记录、待办、提醒、日报、周报、月报、多资料空间均已落地
- 日记模块已升级到富文本方向，并具备历史回看能力
- 待办与番茄条目已建立双向关联链路，可为“项目继承”提供现成入口

当前仍明显缺失的是“项目管理维度”：

- 数据库中尚无 `projects` 表
- `todos` / `pomodoro_entries` 尚无 `project_id` 字段
- UI 中没有项目管理入口、项目筛选器或项目归属展示
- AI 日报虽然强调“按项目分类”，但当前更接近“按标签/内容归纳”，缺少稳定项目主键

### 0.2 本文假设

若以下假设不成立，需要在你确认时指出：

1. “项目”是长期稳定对象，生命周期长于单条待办和单次番茄记录。
2. 一个待办在首版只归属一个项目；一个番茄记录在首版也只归属一个项目。
3. 首版不引入项目成员、项目权限、多层级子项目。
4. 首版不做跨 Profile 的项目共享；项目数据严格跟随当前资料空间隔离。
5. 首版优先解决“归属、展示、统计、报告”闭环，不追求甘特图、里程碑等重型 PM 能力。

---

## 1. 背景与问题

当前系统已经能记录“做了什么”，但还不能稳定回答“这是为哪个项目做的”。这会产生几个实际问题：

- 标签是扁平的，容易混入“开发 / 测试 / 会议”这类工作类型标签，无法等价替代项目归属
- 同一项目跨多天、多待办、多番茄后，难以做稳定汇总
- AI 日报、周报、月报虽然已经可生成，但缺少可靠的项目主键，输出质量受限
- 当用户同时推进多个项目时，今日看板和历史报告难以快速看出时间投向
- 后续若做同步、长期分析、目标追踪，缺少项目层会让数据模型先天偏弱

结论：

“项目管理维度”不是装饰性功能，而是当前记录体系从“碎片日志”走向“可归因工作台”的关键一层。

---

## 2. 设计目标

### 2.1 核心目标

在不推翻现有四层架构的前提下，为系统增加稳定的项目实体，并打通以下链路：

- 创建 / 重命名 / 归档项目
- 待办归属项目
- 番茄记录归属项目
- 弹窗提交、手动补录、编辑条目时可选择项目
- 若番茄关联待办，则默认继承待办所属项目
- 主窗口时间轴、日报、历史报告可展示项目归属
- AI 日报 / 周报 / 月报按项目优先分组

### 2.2 成功标准

满足以下条件，视为首版达标：

1. 用户可以在 UI 中管理项目，且归档项目不会污染日常选择列表。
2. 新建或编辑待办时可绑定项目。
3. 新增、编辑或弹窗提交番茄记录时可绑定项目，且与待办联动时能自动继承。
4. 数据库查询能稳定返回项目名称、颜色、图标等展示信息。
5. 报告生成时可按项目分组，未归属条目也有明确兜底分组。
6. 相关功能在多 Profile 模式下保持严格隔离。

### 2.3 本次不做

- 子项目 / 项目树
- 项目预算、里程碑、看板泳道
- 团队协作、权限、共享项目
- 项目级云同步策略
- 项目模板市场或插件化项目类型

## 3. 现状基线

### 3.1 已有能力，可直接复用

- `src/core/database.py` 已集中承载 schema 与 migration，适合新增项目表和外键字段
- `src/app.py` 已打通弹窗、主窗口、报告窗口的编排链路，适合作为项目选择值的汇流层
- `PopupWindow`、手动补录、条目编辑、待办编辑已经具备“关联待办”交互，可复用为项目归属入口
- `src/ui/report_window.py` 与 `src/services/ai_client.py` 已支持日报/周报/月报生成，便于把项目摘要注入 Prompt
- 多资料空间已完成，天然满足项目数据按 Profile 隔离

### 3.2 当前缺口

- 无 `projects` 数据表及 CRUD API
- 无项目到待办/番茄的关联字段与查询 JOIN
- 无统一项目下拉组件
- 无项目归档态过滤策略
- 无项目维度统计或报告分组逻辑

## 4. 产品方案

### 4.1 项目对象定义

首版项目对象包含：

- `id`: 数据库主键
- `name`: 项目名称，当前 Profile 内唯一
- `color`: UI 展示色
- `icon`: 简短 emoji 或符号
- `archived`: 是否归档
- `created_at`
- `updated_at`

设计原则：

- 项目是“归属对象”，不是标签集合
- 项目数量预期远小于待办和番茄条目，允许在 UI 中用下拉框或列表管理
- 归档项目默认不出现在新建/编辑选择列表，但历史记录仍可正常显示

### 4.2 用户可见能力

#### A. 项目管理页

建议放在设置窗口新增独立页签或在现有管理区中增加“项目管理”板块。

首版支持：

- 创建项目
- 编辑项目名称 / 颜色 / 图标
- 归档项目
- 查看项目基础统计：关联待办数、关联番茄数

首版不支持：

- 删除项目

原因：

删除会直接引入级联清理、历史条目归属丢失、报告数据回溯不一致等问题。首版用“归档”替代删除，更稳妥。

#### B. 待办归属项目

在待办创建/编辑表单中新增项目选择：

- 默认值为“未归属项目”
- 只列出未归档项目
- 保存后待办卡片可展示项目标识

#### C. 番茄记录归属项目

在以下入口新增项目选择或自动继承：

- 弹窗记录窗口
- 手动补录窗口
- 编辑条目窗口

交互规则：

1. 若用户先选了待办，且该待办已有项目，则默认填充对应项目。
2. 用户仍可手动改为其他项目，但需要以显式选择为准。
3. 若没有待办关联，则项目可独立选择。

#### D. 展示与筛选

首版建议补齐以下展示：

- 今日时间轴条目显示项目图标 + 项目名
- 待办列表显示项目归属
- 历史报告/报告窗口中显示项目分组
- 无项目归属时使用“未归属项目”兜底

是否加入项目筛选器，可放到第二步确认后再定：

- 若本轮控制范围，可先只做展示，不做筛选
- 若你更关注“按项目切换视图”，则应把主窗口筛选一并纳入首版

## 5. 技术方案

### 5.1 数据模型

建议新增表：

```sql
CREATE TABLE projects (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL,
    color       TEXT NOT NULL DEFAULT '#ef5350',
    icon        TEXT NOT NULL DEFAULT '📁',
    archived    INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    UNIQUE(name)
);
```

建议扩展字段：

```sql
ALTER TABLE todos ADD COLUMN project_id INTEGER REFERENCES projects(id) ON DELETE SET NULL;
ALTER TABLE pomodoro_entries ADD COLUMN project_id INTEGER REFERENCES projects(id) ON DELETE SET NULL;
```

补充说明：

- `ON DELETE SET NULL` 主要为未来保留；首版 UI 不提供删除项目，但 schema 层先保持安全退路
- `UNIQUE(name)` 作用域为当前 Profile 数据库，天然满足资料空间隔离

### 5.2 Database 层改造

在 `src/core/database.py` 新增或扩展：

- `create_project(...)`
- `update_project(...)`
- `archive_project(project_id)`
- `list_projects(include_archived=False)`
- `get_project(project_id)`
- `get_project_stats(project_id)`

并扩展以下现有链路：

- `add_entry(...)` / `update_entry(...)` 接受 `project_id`
- `get_entries_by_date(...)` JOIN `projects` 返回项目展示字段
- todo CRUD 支持 `project_id`
- 日期范围 todo 查询保留项目信息，供报告使用

### 5.3 服务与编排层

建议保持现有分层，不单独引入重型 service。首版优先用 `Database` 提供项目 CRUD，并由 UI 直接消费，原因是：

- 项目逻辑首版仍以简单增删改查为主
- 当前 app/service 层已经偏轻，过早引入 `ProjectService` 价值有限

但需要在 `src/app.py` 做好入口注入：

- 打开项目管理页
- 报告生成时收集项目信息
- 弹窗提交时处理 todo -> project 继承逻辑

### 5.4 UI 组件建议

建议抽一个可复用的项目选择组件，避免项目下拉在多个窗口重复实现。

推荐新增：

- `src/ui/project_selector.py`

组件职责：

- 加载未归档项目列表
- 支持“未归属项目”选项
- 提供 `set_project_id()` / `project_id()`
- 可在待办表单、弹窗、手动补录、编辑对话框复用

项目管理页建议放在：

- `src/ui/settings_window.py`

原因：

- 资料空间、AI 配置、提醒等管理项已集中在设置中
- “项目”更接近长期配置对象，而非一次性动作

### 5.5 AI 报告集成

在 `src/services/ai_client.py` 的 Prompt 构造中注入项目维度摘要：

- 按项目分组条目
- 输出每个项目的番茄数 / 时间投入 / 代表事项
- 对无项目归属条目使用“未归属项目”分组

这样日报/周报/月报的“按项目分类”将由数据层显式支持，而不是只依赖模型自行理解文本。

- 旧条目默认 `project_id = NULL`
- 没有项目数据时，应用应保持现有体验，不得因为项目功能未配置而阻塞主流程
- 现有待办-番茄关联链路不得回归

## 7. 风险与权衡

### 风险 1：UI 入口过多，交互负担上升

风险：

- 弹窗、补录、编辑、待办都加入项目选择后，界面可能变得拥挤

应对：

- 通过“待办继承项目”减少重复选择
- 允许项目为空
- 项目选择控件保持紧凑，不抢主输入区空间

### 风险 2：项目与标签职责重叠

风险：

- 用户可能不清楚“项目”和“标签”该怎么分

应对：

- 在 UI 文案上明确区分：项目回答“为了谁/哪个事情”，标签回答“这是什么类型的工作”
- 报告中优先按项目分组，再在项目下保留标签语义

### 风险 3：旧数据没有项目归属

风险：

- 历史数据大量为空，项目统计早期不完整

应对：

- 首版不做复杂回填迁移
- 历史空值统一进入“未归属项目”组
- 后续可再考虑手动批量归属或半自动推荐

### 风险 4：删除项目会破坏历史一致性

风险：

- 真删除将带来历史数据显示断裂

应对：

- 首版禁删，只支持归档

## 8. 测试策略

### 8.1 数据层

- migration 测试：老库升级后存在 `projects` 表和 `project_id` 字段
- CRUD 测试：创建、重命名、归档、列出项目
- 关联测试：todo 与 pomodoro 写入/读取 `project_id`
- JOIN 测试：日期查询、报告查询可返回项目展示字段

### 8.2 UI 层

- 项目选择器空状态 / 普通状态 / 归档过滤
- 待办编辑绑定项目
- 弹窗选择待办后自动继承项目
- 手动改写项目后保存正确
- 时间轴 / 列表 / 报告预览中正确展示项目标识

### 8.3 回归要求

必须重点回归：

- 番茄主流程提交
- 待办 CRUD
- 周报 / 月报生成
- 多 Profile 隔离
- diary 富文本相关测试不受影响

## 9. 实施边界

### Always

- 继续沿用 `src/core/database.py` 集中管理 schema 和查询
- 使用绝对导入
- 保持项目数据严格跟随当前 Profile
- 为新增 UI 交互补充正常路径、边界路径和异常路径测试

### Ask First

- 是否把“主窗口按项目筛选”纳入首版
- 是否允许项目颜色/图标自由输入，还是提供受控候选集
- 是否在本轮加入历史条目的项目批量修正工具

### Never

- 不引入新线程
- 不跳过 migration 兼容处理
- 不在多个 UI 文件里重复散落项目列表查询逻辑
- 不以标签字段冒充项目主键

---

## 10. 推荐结论

建议将“项目管理维度”作为下一开发功能项进入门禁流程，原因是：

1. 它是路线图中仍未落地的高价值主干能力。
2. 它能直接提升日报、周报、月报和统计结果的结构化质量。
3. 它与现有待办-番茄关联、报告、多 Profile 架构天然兼容，落地路径清晰。
4. 它比同步、插件系统更贴近当前单机效率工具的核心价值闭环。

## 11. 待你确认的问题

请重点确认这 3 点：

1. 下一项功能是否就按“项目管理维度”推进。
2. 首版是否只做“展示 + 归属 + 报告分组”，暂不做主窗口项目筛选。
3. 项目管理首版是否接受“只归档不删除”的保守策略。
